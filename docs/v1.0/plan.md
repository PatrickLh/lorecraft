# LoreCraft v1.0 执行计划

依据：`docs/v1.0/requirement.md`

评估日期：2026-10-10
状态：可进入实施；以下补充规则为本计划的建议默认值，尚非已经验证的产品结论。

## 1. 需求充分性结论

**现有需求足够构建个人原型，并形成可执行计划。** 已明确产品目标、核心循环、代码权威状态、LLM 输出契约、技术栈、首发范围和验收标准。当前仓库只有需求文档与空 README，实施从工程初始化开始。

需求尚不是完整的实现规格：世界剧本、部分状态转换、异常处理和存档契约需要补齐。这些可以在开发中按下述默认规则落地，不阻塞启动。模型实际能力、叙事效果与数值平衡需要通过真实调用和试玩验证，不能仅凭文档确认。

## 2. 实施前统一的规则

| 问题 | 建议默认规则 |
| --- | --- |
| 世界通关与局终关系 | 世界通关不结束 run：结算世界奖励、提炼该世界记忆、返回枢纽，继续使用同一寿命池；死亡才结束 run。三个世界均完成后显示原型完成提示，允许后续新局，不额外引入胜利终局系统。 |
| 首次解锁与重复奖励 | 初始仅解锁《午夜便利店》，依次解锁《青云门外门》《风雪山庄》。同一 run 每个世界最多完成一次；新 run 可再次进入。每次世界完成获得当前寿命 +15，但跨局上限 +5 仅在该世界首次永久通关时发放，避免重复刷取。 |
| 寿命上限 | 当前寿命限制在 0 至本局寿命上限。局中首次通关使继承层上限 +5，下一局生效，本局上限保持开局快照。事件只调整当前寿命，不调整上限；需求附录中“事件抬升上限”按正文 4.2 处理。 |
| 重开属性 | “局内清零”指重置为 CON/MIND/AGI 各 10、物品与标签为空，寿命为继承后的上限；不得把属性设置为 0。 |
| 回合结算顺序 | 校验完整申报 → 扣基础寿命 1 并应用合法事件增减、属性/物品/标签/flag → 截断数值 → 判死 → 推进幕表及判定通关 → 发放奖励 → 持久化。死亡优先于通关，死亡回合不发通关奖励；同回合事件可抵消基础寿命消耗。 |
| 异常回合 | 玩家确认提交且后端接受后，最终成功或降级均算一个回合，扣寿命 1。降级不应用任何 LLM 状态变更；“状态不变”解释为无申报变更，不免除基础消耗。使用确定的中文环境叙事，不能直接展示无效输出。 |
| 重试范围 | schema、范围、白名单、合法性校验失败及可恢复的请求错误共用最多一次重试预算；超时或再失败即降级。避免 SDK 隐式重试叠加。 |
| flag 权威性 | 世界显式声明全部 flag 及必要的前置 flag，LLM 不能跳过前置条件。flag 只从 false 变为 true；世界进入时初始化，跨局不继承。数值越界或非法申报整份拒绝，不静默截取部分申报。 |
| 幕表与叙事 | 回合请求包含当前幕、可达 flag 和下一幕信息；结算后 UI 显示幕转换/通关/死亡提示，不为转场追加一次 LLM 调用。叙事与权威状态冲突时状态为准并记日志。 |
| 入场 | 枢纽与世界选择不扣寿命；展示手写 intro 和初始建议行动，不为入场单独调用 LLM。 |
| 记忆生命周期 | 通关提炼本世界新增经历，死亡提炼尚未结算经历，避免重复提炼。每次新增最多 5 条、每条最多 50 个 Unicode 字符；保留最多 20 条。超限请求 LLM 合并，失败则去重并淘汰最旧条目。 |
| 记忆调用失败 | 不阻塞通关、死亡和继承奖励；保留旧记忆、标记提炼待重试，允许手动重试且不能重复发奖。 |
| 流式输出 | 服务端解析结构化流，只发送可解析的 narrative 字段增量，前端标记为待确认。完整输出通过校验、事务提交后才发布最终状态；失败时替换暂存叙事。provider 不支持可靠增量解析时退化为完整结果展示，优先保证状态一致。 |
| 物品身份 | 给物品分配稳定 ID，内部按 ID 删除；为兼容需求中的名称列表，适配层仅在名称唯一时解析名称，重名删除拒绝。限制物品、标签、输入和输出长度，具体限额集中配置。 |
| dangerProposal | 当前 TurnOutput 未定义该字段，v1.0 不加入协议；所有危险仅通过 narrative 和受限 attributeDelta 表达。 |
| 单机存档 | 一个活跃 run；页面刷新恢复快照。禁止在活跃 run 未死亡时无提示覆盖；暂不增加放弃局机制。 |

这些规则应在第一阶段同步到实现规格及测试中。若产品意图调整，先修改规则与对应验收，再进入依赖该规则的实现。

## 3. 工程与模块边界

- `apps/web`：Vue 3、TypeScript、Vite；枢纽、世界界面、状态侧栏、建议行动、存档恢复和请求状态。
- `apps/server`：Node、Hono、SQLite；拥有权威状态，执行回合编排、事务、幂等和日志；仅绑定本地地址。
- `packages/core`：状态类型、常量、纯函数 reducer、申报校验、幕推进、死亡判定和继承规则。前端共享类型，不自行提交权威结果。
- `packages/worlddata`：三个手写世界、flag 声明及前置条件、NPC 简介和数据完整性检查。
- `packages/llm`：provider 接口、输出 schema、prompt、流式适配、记忆提炼、摘要与用量记录；不直接写数据库。

统一运行时 schema 与 TypeScript 类型，避免两份契约漂移。初始化 pnpm workspace、类型检查、测试和构建命令；服务端密钥使用 `.env`，提交 `.env.example`，忽略密钥、SQLite 文件和日志。模型名、超时、上下文预算、数值与长度限制均使用配置，不将需求中的价格估算作为成本计算依据。

## 4. 分阶段任务与完成条件

### P0：收敛规格与初始化

- [ ] 固化第 2 节规则，定义 RunState、MetaState、WorldVisit、TurnRecord、MemoryRecord 及 run/世界阶段枚举。
- [ ] 建立 monorepo、基础配置、共享 schema 和统一常量表。
- [ ] 提供不依赖 API key 的 mock provider，返回可控成功、死亡、通关与异常输出。
- [ ] README 写明安装、环境变量、启动与验证命令。

完成条件：干净环境可启动前后端；工作区类型检查和构建通过；mock 可独立调用。

### P1：规则引擎与世界数据

- [ ] 实现新局、进入世界、回合提交、幕推进、通关、死亡、继承与下一世界选择的纯状态转换。
- [ ] 实现三关校验、数值截断、死亡优先级、一次性奖励及 flag 前置约束。
- [ ] 为三个世界补齐约三幕的完整剧本：规则、NPC、危险、全部 flag、前置关系、主目标、初始建议行动和 balanceHint。
- [ ] 每个世界提供一条可达通关路径和典型危险路径；检查引用有效、目标可达、解锁关系无错误。仅 milestoneFlags 中出现的 flag 不足以表达完整剧情，应显式声明 flag 库。
- [ ] 首先完成《午夜便利店》用于端到端接入，再完成其余两个世界。

完成条件：纯规则测试覆盖共享寿命、三种死亡、越界申报、非法 flag、物品删除、幕推进、死亡与通关同回合、重复结算和下一局继承；世界数据检查全部通过。

### P2：存档与后端 API

- [ ] SQLite 建立版本化迁移：`runs` 保存快照和版本，`meta` 保存继承状态，`logs` 保存回合、世界结算、死亡历史、请求结果、用量及错误；提炼任务保存处理状态。
- [ ] 实现存档仓储和事务：一次回合的快照、记录、奖励及继承更新原子提交。
- [ ] 按 run 串行执行请求；客户端提供 requestId，服务端使用版本校验与幂等记录，防止双击、重复发送和并发多扣寿命。
- [ ] LLM 调用在事务外进行，提交前重新验证版本；进程中断后客户端可查询已提交结果或重试同一 requestId。
- [ ] 实现以下 API，并统一错误格式、状态码和请求长度限制。

| API | 用途 |
| --- | --- |
| `GET /api/meta`、`GET /api/worlds` | 继承与世界目录 |
| `POST /api/runs` | 创建新局，拒绝覆盖活跃局 |
| `GET /api/runs/active`、`GET /api/runs/:id` | 恢复当前局及查询状态 |
| `POST /api/runs/:id/enter-world` | 验证解锁及进入资格 |
| `POST /api/runs/:id/turn` | 执行回合，SSE 返回暂存叙事与最终结果 |
| `POST /api/runs/:id/settle` | 幂等完成符合条件的世界/死亡结算，不接受客户端自报奖励 |
| `POST /api/runs/:id/memory/retry` | 重试待处理记忆提炼 |

完成条件：API 集成测试验证恢复、并发/重复提交、事务回滚、非游玩阶段拒绝行动、未解锁世界拒绝进入和结算幂等；mock 完整循环可经 API 跑通。

### P3：LLM 接入与上下文

- [ ] 实现 mock、DeepSeek、Claude 的统一 adapter；实施时查阅各 provider 官方文档确认结构化输出与流能力，使用配置指定模型。
- [ ] prompt 注入世界规则、当前幕、可达 flag、权威状态、继承记忆、摘要和近期历史；明确模型只申报变化。
- [ ] 严格执行 TurnOutput schema、2–3 条建议行动、中文叙事目标和完整申报校验；错误反馈后最多重试一次。
- [ ] 实现超时、断流、JSON 不完整、非法申报等失败的环境回合降级；降级扣寿命后仍执行死亡判定。
- [ ] 实现通关/死亡记忆提炼与超限合并；失败不影响权威结算。
- [ ] 默认每 10 回合尝试滚动摘要，保留近期完整历史；摘要失败保留既有数据，按上下文预算限制请求，不能无限扩大 prompt。
- [ ] 日志记录 provider、模型、时延、token、重试和降级原因；不记录 key。费用仅在配置单价后估算。

完成条件：provider 契约测试和错误注入通过；至少完成一次 DeepSeek 真实结构化调用及记忆提炼；Claude 可配置切换，有可用 key 时做实际冒烟验证，否则明确标记未验证。

### P4：前端完整循环

- [ ] 枢纽显示寿命/上限、记忆、解锁世界、死亡历史及下一世界/重开操作。
- [ ] 世界界面显示中文叙事、自由输入、建议行动、寿命条、三属性、物品、标签及当前幕。
- [ ] 行动提交后禁止重复操作；区分等待、暂存流、已提交、降级和连接中断，最终以服务端快照更新状态。
- [ ] 通关返回枢纽，死亡展示死因与继承结果；记忆失败显示待重试状态。
- [ ] 刷新恢复当前局；断流后查询服务端结果，避免直接新建行动导致重复扣除。
- [ ] 先完成 mock 的便利店垂直流程，再接真实 provider 和剩余世界。

完成条件：浏览器可独立完成开局、跨世界、死亡、继承、重开、刷新恢复及异常恢复；普通使用不需要手动修改数据库。

### P5：验收、试玩与交付

- [ ] 用可控 mock 自动验证下表中的规则与异常用例。
- [ ] 用真实模型试玩便利店 → 青云门 → 风雪山庄，记录寿命消耗、节奏、flag 可达性、记忆引用和叙事/状态冲突。
- [ ] 按试玩结果调整 prompt、剧本和常量；不为赶进度扩大 v1.0 范围。
- [ ] README 补齐 provider 配置、存档位置、重置/备份方法、验证命令和已知限制；保存验收记录及脱敏样例。

完成条件：需求六项验收全部有证据；自动检查通过，真实模型完成通关线与死亡线，任何未验证的 provider 能力单独列明。

## 5. 验收矩阵

| 需求/补充检查 | 验证方式与预期 |
| --- | --- |
| 同局跨 ≥2 世界 | 通关便利店后进入青云门，run ID 不变；寿命为前一世界结算值而非重置值。 |
| 继承可感知 | 死亡后新局 prompt 包含已保存记忆；保存真实叙事中明确引用记忆的样例，不能以 mock 文本代替质量验收。 |
| 通关线与死亡线 | 通关进入枢纽并解锁下一世界；死亡结束局并可创建继承后的新局。 |
| 三种死亡 | 分别使寿命、CON、MIND 归零，断言终局和记录正确；AGI 归零不死亡。 |
| LLM 异常 | 无效 JSON、越界、非法 flag、超时、断流分别注入，最多一次重试；失败后环境回合可继续或按数值死亡，存档可恢复。 |
| 寿命上限继承 | 首次永久通关后下一局上限 65；再次通关同世界仍为 65，第二个首次通关后为 70。 |
| 重复请求/结算 | 相同 requestId 返回同一结果，寿命、物品、奖励和记忆任务不重复；并发请求不覆盖快照。 |
| 记忆/摘要失败 | 结算和存档仍成功，旧记忆保留；重试不重复奖励，上下文仍受预算约束。 |
| 世界与属性重置 | 跨世界保留属性/物品，重开恢复初始属性与空物品；世界 flag 不串到其他世界。 |

## 6. 执行顺序与风险控制

执行依赖为 **P0 → P1 → P2 → P3 → P4 → P5**；P4 的 mock 界面可在 P2 后提前接入。先打通一个世界的垂直流程，再扩展完整三世界，最终交付范围仍为三个世界。

主要风险是模型申报与叙事不一致、flag 推进过快/过慢、流式 JSON 难处理，以及记忆提炼丢失。分别通过权威状态与约束 prompt、真实试玩、暂存流与校验后发布、可重试提炼任务处理。自动测试证明规则与恢复能力，真实试玩证明叙事效果，两者均不可替代。

本计划只安排开发与验证，不包含账号、付费、多用户、动态世界生成、额外检定引擎或部署产品化。当前任务到计划落盘为止，不开始实施代码。
